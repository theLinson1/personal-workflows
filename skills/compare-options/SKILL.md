# 比较取舍

输出能帮助用户作决定的理由和证据，不把 AI 的建议归为用户已作出的判断。

## 确定决策边界

找出要决定什么、什么已决定、当前约束和决策期限。从代码、文档或用户明确说明中取得 context；未知项标清。候选方法可以试用，不意味着用户已认可某种工程范式。

## 比较真正不同的路径

选择实际可行且差别足以影响结果的路径。保留现状可能是合理候选；已被约束排除的路线无需凑数。

使用本次决定最相关的少量维度，例如用户收益、实施和维护成本、平台能力、行为一致性、团队掌握程度、迁移期间的兼容性、回退难度。不要给缺少依据的维度打精确分数。

对每条路径记录关键依据、最大的未证实前提，以及失败后怎样恢复。对推荐补充：什么新证据会使推荐改变，最便宜的验证是什么。

## 保持技术边界可见

迁移类任务先区分目标与实现手段：要解决的是重复维护、行为差异、交付效率，还是别的实际问题，必须由 context 支持。以 KMP 为例，共享逻辑和共享 UI 是不同范围；不能仅根据技术名推定二者都需要。这个例子不代表当前公司已选了任何路线。

遇到版本、兼容性和平台限制，以项目锁定版本和相应官方文档为证据，注明哪些没有查证。

## 给出可行动结论

简述推荐、理由、接受的代价、关键未知和下一步验证。必要时使用对照表；不固定要求 3 个方案。

已授权的可逆实现可继续做。方向变更涉及用户尚未决定的重大取舍时，把可审核方案准备好再提问。后续用户的选择和修正另行记录，不把未回复视为同意。
