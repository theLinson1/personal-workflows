# 需求与假设分级

用于未知会改变产品行为、接口、交付范围或验证标准的任务。这里只迁入本地 requirements-closure 的判断方法；不要求完整固定报告，也不依赖另一个规划 skill。

| 类型 | 判断 | 处理 |
|---|---|---|
| P0 阻塞 | 错误选择会改变尚未决定的用户行为、核心目标、架构责任或发布安全 | 写明阻塞哪个决定或实施步骤，查证或向决策者提出最小问题；并行推进不依赖它的工作 |
| P1 可假设 | 有现有模式或资料支持、影响可控、可以验证的实现选择 | 记录假设、依据、出错影响、验证办法，以及假设不成立时改变什么 |
| P2 可延后 | 不改变用户承诺和主要设计的细节 | 指定在何时、哪一步或什么触发条件下解决 |

P0 不自动阻塞全部任务。例如迁移是否包含 UI 未定，可以先分析当前依赖与两条路线，但不能把 UI 迁移写成已经批准的需求。

复杂任务可用一张表：

| 未知或假设 | 来源/缺口 | 类型 | 阻塞的决定或步骤 | 验证/解决动作 | 最晚解决时机 |
|---|---|---|---|---|---|

仅检查当前相关的行为、成功标准、失败与降级、服务端/客户端能力、观测方式；涉及实验时再看分组与指标口径，涉及上线时再看范围和回退。没有实验的任务不必补 AB 表。

分别判断：问题是否足够清楚以比较方案；方案是否足以形成最终约定；某个实施步骤是否已有必要输入。不要用一个笼统的“已准备好”替代这三个判断。

若用户需要先看探索稿，明确标注候选行为、假设和未定处，不把草案冒充可执行规格。已经明确的范围或已授权动作不重新提问；仍缺必要决定时，提问针对具体未定项。
